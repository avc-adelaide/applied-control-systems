\CONCEPT[7]{Weeks 7--9: Practical project --- Ping pong rig control}

\begin{frame}
\frametitle{Introduction}
In this practical project, you will apply control theory concepts to design and implement a position controller for a new piece of hardware: the ping pong rig. This plant is more challenging to control than the QUBE used in previous practicals, and it emphasises the versatility of the PID control methodology.
\end{frame}


\SUBCONCEPT{Problem statement}

\begin{frame}{Problem statement}
In this project, you are provided with a hardware rig that needs to be controlled.
\begin{itemize}
\item Using your best engineering judgement, you are required to implement a position controller for the height of the ping pong ball
\item As part of the documentation, a complete description of the hardware and interfaces is required
\item In order to achieve setpoint following, calibration of the position sensor is required
\item No fixed performance criteria are specified; in your documentation you must justify how you tuned the controller and attempted to optimise the performance of the closed-loop system
\item While a relatively simple PID controller in its `pure' form will manage to control this plant, we encourage creativity (signal processing, fudge factors, gain scheduling, etc.) to improve performance
\end{itemize}
\end{frame}

\begin{frame}
\frametitle{}
The project consists of three parts, preceded by setting up the rig:
\begin{itemize}
\item Getting started: hardware and software setup
\item Part A: System identification and modelling (interfacing, calibration, characterisation)
\item Part B: Controller design and tuning
\item Part C: Performance evaluation and analysis
\end{itemize}
Work in groups of around 2--3 (depending on class size and number of rigs). You will be assessed via a formal group report.
\end{frame}

\begin{frame}
\frametitle{Timing}

\begin{itemize}
\item Each part should take approximately \emph{no more than} one week to complete.
\item If you finish one part before the end of a session, don't stop there --- keep going.
\item Plan to write up the report as you go, as it will also take time to put together. Each part ends with a checklist of what to record for the report while you still have access to the rig.
\item Manage your time and progress carefully. A final (fourth) prac session will be held in the final week of semester to allow for finishing up, but no sessions are planned for SWOTVAC.
\end{itemize}
\end{frame}

\begin{frame}{Setting up hardware (CARM)}
In your group, follow these steps:
\begin{enumerate}
	\item Do not connect the rig to the power supply
	\item Connect the ping pong rig output labelled \textsf{Distance} to channel \textsf{AI 0} on the data acquisition board
	\item Connect the ping pong rig input labelled \textsf{Fan Input} to channel \textsf{AO 0} on the data acquisition board
	\item Ensure the gain knob is rotated all the way to the right (minimum gain)
	\item Connect the rig to the power supply
\end{enumerate}
\end{frame}

\begin{frame}{Setting up software (CARM)}
	Open Simulink and create a blank model. In this project you are going to create your own model for the ping pong rig. Three blocks initialise the hardware and send/receive signals to/from the physical rig:
	\begin{itemize}
		\item \textsf{HIL Initialize}: hardware initialisation
		\item \textsf{HIL Read Analog}: receive analogue signal (voltage)
		\item \textsf{HIL Write Analog}: send analogue signal (voltage)
	\end{itemize}
	Find these three blocks in the \textsf{Library Browser} and drag them into your model. Double-click the \textsf{HIL Read/Write} blocks and ensure channel 0 is selected. Double-click \textsf{HIL Initialize} and choose the \textsf{PCIE 6321} board under the \textsf{Board Type} section.

	% TODO: confirm the exact option names in HIL Initialize > Analog Outputs at the rig
	The fan holds the last voltage it was sent when the model stops. So that it switches off at the end of each run, also set the final output voltage (applied when the model terminates) to \qty{0}{V} in the \textsf{Analog Outputs} settings of \textsf{HIL Initialize}.
\end{frame}

\begin{frame}{Setting up software}
	Select the three blocks, then right-click and select \textsf{Create Subsystem from Selection}. This is now your ping pong plant, which has an input and an output; you can label them as shown below.

	The \textsf{To Workspace} block exports the sensor data to MATLAB. Set up the \textsf{Step} block with a step time of \texttt{0} and a final value between \qty{1}{V} and \qty{10}{V}, then run the model. You may need to increase the input voltage to increase the upward force provided by the fan.

\begin{frame}{Running the system}
	To run on hardware go to \textsf{Modelling} $\to$ \textsf{Model Settings} $\to$ \textsf{Code Generation} $\to$ \textsf{Browse} and choose \texttt{quarc\_win64.tlc}; the \textsf{Hardware} tab should now appear.

	The \textsf{To Workspace} block may lose data points while the model is running. To prevent this, go to \textsf{Modelling} $\to$ \textsf{Model Settings} $\to$ \textsf{Solver} $\to$ \textsf{Solver details} and set the fixed-step size to \qty{0.01}{s}. Quarc runs the model in Simulink External Mode, whose data buffer holds 1000 samples per run by default, so with this step size set the \textsf{Stop Time} to \qty{9.99}{s}.

	Try running the system to get the ping pong ball to lift into the tube by adding a step input to the system. You may have to play around with the input voltage to get the ball to lift.
\end{frame}

\SUBCONCEPT{Part A: System identification and modelling}

\begin{frame}{Interfacing}
Before modelling the plant you need a clear picture of its signals:
\begin{itemize}
\item Identify the inputs and outputs, and the range of each electrical signal
\item Calibrate the sensor signal (the plant output; next slide) so the controller works in units of distance
\item Bound the control signal sent to the fan (the plant input): the controller must never command a voltage outside the fan's allowable input range (e.g.\ use a \textsf{Saturation} block before \textsf{HIL Write Analog})
\end{itemize}
\end{frame}

\begin{frame}{Calibration: voltage to distance conversion}
	After getting the ping pong ball to lift, you may notice that the output is not in units of distance. You will need to calibrate the sensor (i.e.\ convert volts to a unit of distance).
\begin{itemize}
\item Record the \emph{sensor output} voltage (not the fan input voltage!) with the ball at known heights, using the \qty{10}{cm} markings on the side of the tube
\item Use at least two data points to fit a linear relationship between sensor voltage and distance; more points will show whether the sensor is linear over the full height of the tube
\item Implement this conversion with \textsf{Gain} and \textsf{Constant} blocks, as shown below
\end{itemize}
\begin{figure}
	\centering
	\includegraphics[width=8cm]{project_conversion}
\end{figure}
\end{frame}

\begin{frame}{Conditioning the measurement}
Once calibrated, you will notice that the sensor is heavily discretised, making analysis difficult; the discretisation would also cause large spikes in the derivative term, limiting the effectiveness of a controller.

As in previous practicals, filter the measured height to smooth the signal without introducing too much time lag, using the low-pass filter method from Practicals 1 and 3 to identify an appropriate cut-off frequency. In the example below the signal is smoother, does not have too much lag, and may be suitable for control purposes.

\begin{figure}
	\centering
	\includegraphics[width=4.8cm]{project_filter}
\end{figure}
\end{frame}

\begin{frame}{Modelling the ping pong rig}
Now that the system has been calibrated and the output conditioned, characterise the dynamics of the plant:
	\begin{itemize}
		\item Run a step response on the rig and plot the data in MATLAB using the \textsf{To Workspace} block
		\item As in Practical 2, fit a straight line to the response to find the Integrator with Time Delay (ITD) parameters $a$ and $\tau$
		\item Determine a transfer function and/or state space model for the plant; consider whether another model form (e.g.\ First Order with Time Delay, FOTD) fits your data better, and justify your choice
		\item Look for nonlinearities: does the response change with the size of the step, or with the height of the ball?
		\item Optionally, characterise the frequency response, as in Practical 5
	\end{itemize}
\end{frame}

\begin{frame}{Part A: What to record for your report}
Part A provides the evidence for rubric criteria 2 (\emph{Systems overview}) and 3 (\emph{Open loop characterisations}). Before moving on, make sure you have:
\begin{itemize}
\item A photo or schematic of the rig, and a signal-flow diagram from fan voltage through to sensor voltage, labelled with the board channels and the range of each signal
\item Your calibration data, the fitted line and its equation, and a comment on how linear the sensor is
\item Raw and filtered measurements on the same axes, the cut-off frequency you chose, and why (noise versus lag)
\item Step response plots with your fitted model overlaid, the model parameters (e.g.\ $a$ and $\tau$), and how you obtained them
\item Evidence for or against nonlinearity, e.g.\ responses to steps of different sizes or at different heights
\end{itemize}
Save the data from every run (e.g.\ as a \texttt{.mat} file with a descriptive name) so you can re-plot it later for high quality figures.
\end{frame}


\SUBCONCEPT{Part B: Controller design and tuning}

\begin{frame}{Initial design}
	With the system set up, calibrated, filtered and characterised, you may start designing a controller. Controller design must be more than trial and error:
	\begin{itemize}
		\item Using your model parameters (e.g.\ $a$ and $\tau$), find PID gains from at least one tuning recipe (e.g.\ the ITD tuning laws from Practical 4)
		\item Implement a closed-loop PID controller in Simulink
	\end{itemize}
\begin{figure}
	\centering
	\includegraphics[width=\textwidth]{project_pid}
\end{figure}
\end{frame}


\begin{frame}{Initial performance}
With these initial gains:
\begin{itemize}
	\item Does the controller stabilise the system?
	\item Does it achieve setpoint following?
	\item How does the controller perform in general? Measure initial performance characteristics (settling time, overshoot, etc.)
\end{itemize}
Your initial controller is unlikely to perform very well. Even if it does, further tuning will improve its performance (Part C).
\end{frame}

\begin{frame}{Part B: What to record for your report}
Part B provides the first half of the evidence for rubric criterion 4 (\emph{Control systems}). Before moving on, make sure you have:
\begin{itemize}
\item The tuning recipe you used, the model parameters it needs, and the calculation of your PID gains
\item A diagram of your closed-loop Simulink model, including the filter and saturation (for the appendix)
\item The closed-loop step response with your initial gains, and the measured performance (e.g.\ settling time, overshoot, steady-state error)
\item A statement of the performance you are aiming for, and what you think limits it on this rig (e.g.\ sensor noise and discretisation, time delay, fan saturation)
\end{itemize}
\end{frame}


\SUBCONCEPT{Part C: Performance evaluation and analysis}

\begin{frame}{Improving performance}
\begin{itemize}
\item Use systematic methods to improve the tuning --- record what you changed, why, and the effect of each change
\item Quantify performance improvements against at least two metrics (e.g.\ overshoot, settling time, \dots)
\item Beyond `pure' PID, consider signal processing, fudge factors, gain scheduling, etc., as encouraged in the problem statement
\end{itemize}
\end{frame}


\begin{frame}{Analysis and testing}
Once you have successfully controlled the ping pong rig, investigate how well your system operates under different conditions. As a minimum:
\begin{itemize}
\item Test against a sweep of step inputs (different amplitudes, different signs)
\item Use at least one approach to test disturbance rejection characteristics
\end{itemize}
Beyond this, try varying some of the system parameters (e.g.\ a ball of different mass), investigate measurement noise, and look for the limits of stability. This investigation will indicate the robustness of your controller.

This part of the project is purposefully open-ended: what do \emph{you} think are important experiments to test the performance of the ping pong rig controller?
\end{frame}

\begin{frame}{Part C: What to record for your report}
Part C completes rubric criterion 4 (\emph{Control systems}) and provides the evidence for criterion 5 (\emph{Performance and robustness}). Make sure you have:
\begin{itemize}
\item A record of each tuning change (e.g.\ a table of gains against your chosen metrics) showing how you got from the initial to the final controller
\item Initial and final step responses on the same axes, with at least two metrics quantified for each
\item Results of the step sweep across different amplitudes and signs
\item Your disturbance rejection test: how the disturbance was applied, and how the controller responded
\item What else you varied, how the performance changed, and where (if anywhere) the loop became unstable
\end{itemize}
In the report, explain \emph{why} each result looks the way it does, rather than only presenting the plots.
\end{frame}


\SUBCONCEPT{Report and assessment}

\begin{frame}{Project report}
	After designing and testing your controller you will describe your process in a formal, professional group report. While the structure is up to you, it must address the rubric criteria (next slide). Suggestions for inclusion are:
	\begin{itemize}
		\item An executive summary (required), introduction and conclusion
		\item A description of the hardware and software, with photo(s) / schematic(s) / flow diagram(s)
		\item A description of the calibration process
		\item A discussion of the open-loop response, the model you fitted to it, and any nonlinearities
		\item An explanation of the tuning process such as what tuning law was used, your method of manual tuning, etc.
		\item An in-depth discussion of the performance and robustness of the controller
		\item Diagrams of Simulink models and MATLAB code placed in an appendix
	\end{itemize}
	Export your data with the \textsf{To Workspace} block and plot it in MATLAB for high quality figures, rather than using screenshots of Simulink scopes.
\end{frame}

\begin{frame}{Rubric}
The project is assessed via a formal report. The rubric includes the following criteria (equally weighted):

\small
\begin{enumerate}
    \item \textbf{Writing Style and Report Formatting}:
    Grammar, spelling, tenses, formality, completeness, flow. Etc. Appropriate introduction and conclusion. Must include executive summary. High quality figures and graphs, typography, typesetting, document structure, tables of contents, figure captions. Etc.

    \item \textbf{Systems overview}:
    Explanation (and possibly derivation) of dynamics, actuator, interfacing with sensor(s), input signals, output signals, ranges of electrical signals. Photo(s) / schematic(s) / flow diagram(s) needed.

    \item \textbf{Open loop characterisations}:
    Sensor calibration, signal normalisation, step responses, nonlinearities, frequency responses. Characterisation of plant model (transfer function, ITD/FOTD parameters, etc., as appropriate).

    \item \textbf{Control systems}:
    Use of at least one tuning recipe, characterising performance (settling time, overshoot, etc.). Manual tuning improvements to improve default response. Discussion of desired performance and obstacles for improving performance.

    \item \textbf{Performance and robustness}:
    Exploration of system behaviour under varying conditions, including but not limited to robustness to parameter variation (e.g., mass variation), measurement noise, disturbances. Changes in performance vs variations. Limits of stability.
\end{enumerate}
\end{frame}
